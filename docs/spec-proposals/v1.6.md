# Spec proposals for v1.6

Spec-ready text, one section per amendment, in the form I would fold into
`docs/spec.md`, as in [`v1.5.md`](v1.5.md). The reasoning is kept short here;
where a decision needs more, it goes in `decisions.md`.

Written against the spec as it stands on `main`, **v1.3**, with v1.5 being
folded separately. Nothing here depends on v1.5's wording except §24.2, which
this extends; section 2 is written so that it reads correctly whether or not
v1.5 §5 has landed.

Opened by v0.6 (Google Drive as a destination).

---

## 1. Corrected — §8.2: what `drive.file` can see

*Rationale: §8.2 says `drive.file` grants access to files the app created or
that the user opened with the app through the Picker. It does not draw the
consequence: that access is **per file**, and everything else in the account
does not exist as far as the token is concerned. The v0.6 plan assumed a test
folder made by hand could be found by name, that §36's "existing file" case
carried over from Dropbox, and that the destination picker could browse the
user's Drive. None of the three holds, and each was caught before code
depended on it only because the plan was written down first.*

Add to §8.2's facts:

- `drive.file` access is **per file**. A file or folder the app did not create,
  and that the user did not open with the app through the Picker, is invisible:
  `files.get` answers `404` for it and `files.list` omits it. This includes
  the user's existing folders in My Drive, and folders of the same name as
  one CloudLug is looking for.
- The grant belongs to the app's Google Cloud project. Whether two OAuth
  clients in one project (CloudLug's Android client and its tooling Desktop
  client) see each other's files is **not documented**; CloudLug keeps both in
  one project and treats cross-client visibility as unverified until observed.

And to §8.2's decision, as item 5:

5. As a destination under `drive.file`, CloudLug can choose **My Drive's root,
   or a folder CloudLug itself created**, and nothing else (§24.2). A user who
   wants the transfer elsewhere moves the enclosing folder in Drive afterwards.
   Moving it does not end CloudLug's access to it or to anything inside it,
   so §19.2's idempotency check still finds every object on a later retry.

And to §36, replacing the Drive half of "Validate `content_hash` and
MD5/SHA-256 … against provider-reported values on real uploads":

- For Drive, the "pre-existing file" case is a **local file the tool uploads**,
  whose bytes the tool did not generate. A file uploaded by another client
  cannot be read under `drive.file`, so that case cannot exist; CloudLug only
  ever verifies objects it uploaded itself, so it never needs to trust another
  uploader's hash either.

## 2. Added — §24.2: choosing a Drive destination, and saying so at review

*Rationale: a product constraint the user will meet on the first Drive
transfer, and should meet on the review screen rather than by looking for their
folders in the picker and not finding them.*

Add to §24.2's destination picker (v1.5 §5, "The destination picker"):

For a destination whose granted scopes see only the app's own files (Google
Drive under `drive.file`, §8.2), the picker offers the **account root** and
the folders CloudLug created, and says why the list is short:

```
My Drive
  Only My Drive and folders CloudLug created are shown.
  CloudLug can't see your other Drive folders with the access it asks for.
```

The picker does not offer to browse the rest of the account, and does not
offer a text field for a folder path or id: neither can be honoured.

Add to §24.2 step 5 (review), after "destination enclosing folder":

The review names **where the enclosing folder will be created**, not only its
name. When that place is the Drive root because the §8.2 constraint left no
other choice, it says so and how to put the folder elsewhere:

```
Destination   Google Drive
Folder        "Dropbox transfer 2026-09-30"
              will be created at the top of My Drive;
              you can move it afterwards in Drive.
```

When the user picked one of CloudLug's own folders, the review names that
folder instead, and the second line is omitted.

## 3. Clarified — §30 and §8.1: a tooling client's secret is not the app's

*Rationale: §8.1 says never embed a client secret in the APK, and `CLAUDE.md`
said "no client secret exists" anywhere. The Drive tools made the second
sentence false. Google retired the out-of-band flow and disallows loopback
redirects for Android clients, so a terminal tool needs a **Desktop** client,
and Google requires a Desktop client's secret at the token endpoint even under
PKCE.*

Add to §30, after the sentence on mobile OAuth client identifiers:

> Developer tooling that cannot use the app's client (for example, a terminal
> tool needing a loopback redirect) may use a separate client of its own. Any
> secret that client has is supplied through the environment at runtime,
> never committed, never compiled into the app, and grants nothing the app's
> own client does not. The app itself remains a public client with no secret
> (§8.1).

## 4. Open — §8.4: the Android redirect for Google

*Not spec-ready wording. A question for the maintainer, raised before the
connector is written, because the answer changes §8.4.*

§8.4 says: AppAuth, Custom Tabs, and a custom-scheme or App Links redirect
validated against the pending PKCE state. The v0.6 plan used Google's
reverse-client-id scheme (`com.googleusercontent.apps.<id>:/oauth2redirect`)
for this.

Google's native-app guide, read 2026-09-30, says: **"Custom URI schemes are no
longer supported on Android and Chrome apps"**, and that loopback redirects on
mobile are deprecated. It points Android apps to Google's Android identity
libraries instead. Those authorize through Google Play services rather than a
browser tab, and hand back an access token rather than a refresh token the app
holds itself.

Three ways forward, in the order I would try them:

1. **The console still allows it for this client.** Some Android OAuth clients
   show an "Enable custom URI scheme" setting under Advanced settings. If this
   one does, §8.4 stands as written, and the risk is recorded: Google has said
   it is unsupported, so it can be withdrawn.
2. **App Links.** A verified `https` redirect on a domain CloudLug controls.
   It needs a hosted `assetlinks.json`, which touches §2.1's "no server of its
   own" in spirit, if not in letter. It also needs a client type that accepts
   an `https` redirect, which Google's Android client does not.
3. **Google's authorization client.** No browser and no refresh token in
   CloudLug's hands: the access token is re-requested from Play services when
   needed, including in the background. That changes §8.3 (nothing to store
   for Drive) and §8.4 (no Custom Tab), and makes Play services a dependency
   of the Drive half of the app.

Decision needed before Step 2's connector.
