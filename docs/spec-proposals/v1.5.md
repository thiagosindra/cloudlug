# Spec proposals for v1.5

Spec-ready text, one section per amendment, in the form I would fold into
`docs/spec.md`. The reasoning lives in `decisions.md`; this file is the wording.

Written against the spec as it stands on `main`, which is **v1.3**. The v1.4
fold does not appear in `docs/spec.md` at the time of writing — see the note at
the end of this file.

---

## 1. Amended — §2.2: reject the same *account*, not the same provider

*Rationale: §2.2 prohibits same-provider transfers in the transfer domain. That
rule was written when a provider and an account were effectively the same
thing, and the prohibition it is reaching for is real — a transfer from an
account to itself is a copy of a tree into its own subtree, which §2.3's
"copy, never synchronize" cannot express sensibly and which can recurse. But
the rule as written also forbids Dropbox → Dropbox between two accounts the
same person owns, which is a legitimate transfer and, as of v0.4, the only one
CloudLug can perform at all.*

Replace §2.2's prohibition with:

A transfer's source and destination must be different **accounts**. Two
accounts at the same provider are a legal pair; one account with itself is not.

```
Allowed:   Dropbox(A) -> Google Drive(B)    Google Drive(B) -> Dropbox(A)
           Dropbox(A) -> Dropbox(B)
Rejected:  Dropbox(A) -> Dropbox(A)
```

The rule stays in the transfer domain rather than in an adapter, as §2.2
already requires: it is a property of the pair, and no single adapter can see
both halves.

### What this changes elsewhere

- **§9** the wizard picks a source **account** and a destination **account**,
  not a provider each. Where a provider has one connected account the two
  choices look the same as before; where it has two they do not, and the
  account is what the user is actually choosing.
- **§7** is what makes the two lists differ: the source list offers accounts
  whose granted scopes permit reading, the destination list those that permit
  writing. An account may appear in both, one, or neither.
- **§12.1** the persisted transfer already records `sourceAccountId` and
  `destinationAccountId`, so nothing in storage changes. The invariant moves
  from comparing providers to comparing those two ids.

### What it does not change

§2.3 still holds: this is a copy, and a destination folder inside the source
selection would be a copy into itself. Same-account is the case that makes that
trivially reachable, which is why it stays rejected; the general case is §10's
enclosing folder and §19.3's collision rules, unchanged.

## 2. Amended — §5: what `enumerate` must emit

*Rationale: §5 says an adapter enumerates a selection and that the walk is
depth-first and resumable. It does not say what the emitted objects have to
contain, and `ManifestBuilder` needs two things §5 never asked for: each
object's `parentId`, which is how a relative path is rebuilt, and the selection
roots themselves, because §10 reproduces the source's own ancestors. The
Dropbox adapter supplied neither — it asked Dropbox for the whole subtree in
one recursive call, which returns entries with no containment between them and
never includes the folder that was asked about. Both adapters passed their
tests. The pairing that ships could not build a manifest at all.*

Add to §5, under `enumerate`:

The flow must emit, in this order:

1. **Every selection root, itself.** A root is an item of the transfer, not a
   cursor into one: §10 reproduces the source's own ancestors, and the folder
   the user selected is the outermost of them.
2. **Each root's descendants, depth-first**, each one after the object that
   contains it.

Every emitted object except a selection root must carry a non-null `parentId`
naming an object the same flow has **already** emitted. A selection root's
`parentId` is not constrained; nothing above the adapter reads it.

A selection root is not necessarily a folder. §9 offers a checkbox on every
row, so a root may be a file, and an adapter must emit it alone rather than
asking the provider to list it.

### Why this is stated rather than assumed

An adapter that satisfies §5's ordering but sets no parents at all is not
obviously broken by inspection, and it is not caught by a contract test that
asks "is each object's parent earlier in the list" — an object with no parent
passes that question by having nothing to check. The requirement has to be
"every object names a parent that came before it", which is a different
assertion and the one §31.2's suite now makes.

### What this costs

An adapter whose API offers a recursive listing may no longer use it as the
whole answer, because the containment is not in that response. Descending a
level at a time is one request per folder rather than one per page. §11 already
ranks a manifest that can be resumed above one that is built quickly, and a
manifest that cannot be built is worth nothing at either speed.

## 3. Amended — §13.1: a preparation that fails leaves PREPARING

*Rationale: §13.1 gives PREPARING the transitions READY, WAITING_FOR_WIFI,
AUTH_REQUIRED, FAILED and CANCELLED, and §24.1 shows every transfer. Nothing
said who moves a transfer out of PREPARING when preparation throws, and nothing
did: the row stayed in PREPARING with no manifest and no process behind it,
which §24.1 then displayed indefinitely as "Preparing — 0 / 0 files".*

Add to §13.1:

A transfer that enters PREPARING must leave it. If preparation does not
complete, the transfer moves to FAILED carrying the provider's error
identifier, or to the state that diagnoses the failure more precisely
(AUTH_REQUIRED, WAITING_FOR_WIFI). Cancelling the work is not a failure: the
transfer stays in PREPARING and §12.1's resume picks it up.

A state that nothing can leave is worse than a failure, because a failure at
least says what happened.

### §24.2 step 5, extended

Step 5 already says a user who reviews a manifest and backs out leaves nothing
behind. The wizard must create the transfer before §11's manifest has anywhere
to be written, so a preparation that fails leaves a row the user never
confirmed and never saw. That row is discarded with its items — a review that
never reached a manifest is abandoned in the strongest sense. This is distinct
from CANCELLED, which is how a transfer the user *did* start goes away, and
which §13.1 keeps.

## 4. Amended — §23: name the failure when the mapping has no case for it

*Rationale: §23 maps provider failures onto neutral kinds and §26 keeps
provider detail out of logs. Between them, a failure with no mapping reached
the user as "Dropbox returned 409" — a status that identifies nothing, because
409 is the status Dropbox uses for its entire route-specific error vocabulary.
The tag that does identify it was being carried on the exception and read by
nobody.*

Add to §23:

Where a provider's failure has no mapping, the message must carry the
provider's own error identifier — the tag, code or reason name, not its prose.
A bare HTTP status is not a diagnosis and is not a report anyone can act on.

This does not weaken §26. An identifier of this kind names which member of a
closed vocabulary was taken; it contains no token, no header, no filename and
no file content. It is the same string §23 already required on the exception's
`code`, and the requirement is only that whatever the user is shown includes
it.

## 5. Added — §24.2: how the pickers behave

*Rationale: §9 describes an in-app browser built on `listChildren`, one level
at a time, which implies descent without ever saying so. §24.2 describes the
wizard's steps without saying what a row does when you touch it. Between the
two, the picker shipped with every row toggling selection and nothing opening a
folder — so only an account's top level could be transferred at all, and
`photos` could be taken whole or not at all. Nothing was violated, because
nothing had been written down.*

Add to §24.2, for both picker steps:

### The browser

Each picker shows the contents of **one folder**, obtained from
`listChildren`, and shows **where it is** — the path from the account root to
the folder on screen. The account root is shown as `/`.

An **Up** control returns to the parent folder; it is absent at the account
root. The platform's own back gesture does the same while there is a level to
return to, and leaves the step only at the top of the tree.

### The source picker

| Touching | Does |
|---|---|
| a folder's row | opens that folder |
| a folder's checkbox | selects that folder whole, without opening it |
| a file's row or checkbox | selects that file |

A selection is **kept while navigating**. It is a set of objects, not of rows
on screen, so it survives descending, ascending and moving to an unrelated
branch — a user selecting from two different folders is the ordinary case, not
an edge one. Because the selected objects can be nowhere near the current
level, the step shows a **count of selected roots**, which is the only evidence
on screen that an earlier pick still stands.

Each root records the **display path** at which it was selected, and §10
reproduces the source's own ancestors there: a root selected at
`/photos/2025/July` lands at `photos/2025/July` under the enclosing folder, not
at `July`. `CloudObject` carries identity rather than a path (§6), so the
browser is the only component that can know this, and it must capture the path
when the selection is made rather than reconstructing it later — by the review
step the browser may be somewhere else entirely.

### The destination picker

The destination is **one folder**, so its rows carry no checkbox or radio:
a row opens the folder it names. A **"Choose this folder"** action takes the
level currently open.

The row that names a folder is the row that opens it. A control meaning
"select" on that same row would leave no way to look inside a folder before
committing a transfer to it, and looking inside is exactly what a user does
before choosing where something lands.

The account root is a legitimate choice, because §10 creates its own enclosing
folder inside whatever is chosen. Only folders are listed: a file is not a
place a transfer can land.

### The review step

§24.2 step 5 asks the user to confirm before any byte moves, and counts alone
cannot be confirmed — they say how much, never what. The review lists **each
selected root at its §10 display path**, which is also the only place the
ancestors the browser walked through become visible.

### Why this is stated rather than left to §9

§9 says the picker browses one level at a time. Everything above follows from
that sentence only if you already know the answer. The shipped picker satisfied
every word of §9 and §24.2 as written, and could not reach a file two folders
down.

## 6. Amended — §4: the modules v0.4 and v0.5 actually added

§4's tree predates three things that now exist. Replace the tree with:

```
cloudlug/
├── app/
├── core/
│   ├── model/
│   ├── database/
│   ├── hashing/
│   ├── network/
│   ├── security/
│   ├── auth/
│   ├── transfer/
│   ├── storage/
│   ├── scheduling/
│   └── ui/
├── providers/
│   ├── api/
│   ├── fake/
│   ├── dropbox/
│   └── google-drive/
├── feature/
│   ├── home/
│   ├── accounts/
│   ├── new-transfer/
│   ├── transfer-details/
│   └── settings/
├── tools/
└── docs/
```

Three changes and one deletion.

`core:scheduling` is §17, and it is a module rather than part of `core:transfer`
because §17 is the only part of the engine's path that cannot be a JVM test:
`JobScheduler`, `WorkManager` and `Notification` are all platform types.
`core:transfer` stays pure Kotlin and keeps the *decision* — which transfers
have work left, and what network each needs — in `SchedulingPolicy`, which is
JVM-testable. `core:scheduling` holds only the two translations of that
decision into platform calls. The dependency runs one way: scheduling depends on
transfer, and nothing in transfer knows a scheduler exists.

`core:auth` and `providers:fake` are in the tree because they are shipped
modules, and have been since v0.2 and v0.1 respectively. `providers:fake` is a
test double that ships: §31.3's contract suite is published from it as test
fixtures, and the debug build offers it as a source so §24.2 can be driven
without an account.

`tools/` holds what is **not** shipped — §36 validation harnesses, the fixture
capture of §31.2, and the §31.4 recovery harness — each of which needs a token,
a network or a device and so is never part of `build` or CI.

`feature/source-picker` and `feature/destination-picker` are removed. Both
pickers are steps of the §24.2 wizard and live in `feature:new-transfer`; a
picker is not a destination anything navigates to.

## 7. Amended — §17: what "correctness must never depend on a worker staying alive" requires

§17's two paths stand as written. What it does not say, and what v0.5 found the
hard way, is what the sentence after them costs.

Add:

> Both paths express §16's network policy as the job's own constraint, so the
> platform stops the job when the policy stops being met. Neither path may
> treat that stop as an error: the transfer moves to the §13.1 waiting state
> that names the condition, and the same constraint is what starts it again.
> The app does not watch connectivity to do this.
>
> A stop is not a pause. Both arrive as a cancelled coroutine, and the engine
> cannot tell them apart, so whatever stops a job is responsible for recording
> why it stopped — before unwinding, and without relying on a stop reason the
> platform may not supply.
>
> Anything that schedules through `JobScheduler` must declare its id range.
> `WorkManager` schedules through `JobScheduler` too, on every API level, so an
> app that also schedules its own jobs has two allocators in one id space and
> whichever schedules second silently cancels the other.

### Why this is stated rather than assumed

Each of the three was a defect in a scheduler that read §17 correctly.

The first: WorkManager enforces a constraint by cancelling the worker. The
engine unwound as it would for a pause, the row still said `RUNNING`, and §24.3
showed "Running" for a transfer that had stopped and would not start again.

The second: the worker reported success, because "the transfer did not
complete" is not a worker failure. The work was then finished, nothing
re-applied the constraint, and the transfer waited for someone to open the app
— which §16 says it must not need.

The third was found by a lint check rather than by a test, and nothing in either
scheduler's own code hints at it, because the overlap is not in either of them.

## 8. Amended — §13.2 and §22.5: what an item that was interrupted goes back to

§22.5 says an expired session is abandoned and "the item restarts from its
cached chunks". §13.2's transition table was read as making `CACHED` that
restarting point. It cannot be, and the two statements have to be reconciled.

Replace §22.5's second sentence with:

> On resume, an expired or uncontinuable session is abandoned and the item
> restarts, never continuing into a partially written destination object.
> Cached chunks are a bounded pipeline between the download and the upload
> (§14, §15.3), not a resume point: §19.4 computes both hashes in the single
> pass that reads the object, and a half-built hash cannot be resumed from. The
> unit of resume is the item.

And add to §13.2:

> Recovery after process death returns **every** active per-object state —
> `CHECKING_DESTINATION`, `DOWNLOADING`, `CACHED`, `UPLOADING`, `VERIFYING` —
> to `PENDING`. Re-running an item is cheap to get right and expensive to skip:
> §19.2's idempotency record and §19.3's destination check both run before any
> byte moves, so an item whose bytes did arrive settles as a duplicate rather
> than being sent twice.

### Why this is stated rather than assumed

The engine begins a file at `CHECKING_DESTINATION`, and neither `CACHED` nor
`VERIFYING` can reach it. An item left in either by process death therefore
threw on the next run and took the whole transfer with it — twice over, because
the upload session recorded on the row outlived the process too, and a session
holding bytes cannot accept a chunk at offset zero.

Both were invisible to every existing test, because every existing test resumes
from a **pause**. A pause unwinds: the coroutine is cancelled, every `finally`
runs, and the rows describe a transfer that stopped tidily. Process death
leaves whatever was written at the instant the process went away. §31.4 asks
for the second and had only ever been run against the first.

## 9. Amended — §33: v0.5 is background execution, and Drive moves down

Ratified by the maintainer before the work began, and recorded here so the
table matches what shipped.

| Milestone | Scope |
|---|---|
| v0.4 — Dropbox → Dropbox | Multi-account Dropbox, both ends the real adapter. |
| v0.5 — Background execution | §17's two paths, §24.4's notification, resume across process death and reboot, §16 enforced as a platform constraint. |
| v0.6 — Google Drive destination | Drive adapter with `drive.file` only. **Dropbox → Drive works end to end.** |

Everything below v0.6 shifts by one. The rationale is that the engine ran in an
app-scoped coroutine and died with the process: a transfer measured in hours
could not survive the user leaving the app, which made every later milestone's
device testing a test of something nobody would ship.

## A note on v1.4

`docs/spec.md` on `main` is still v1.3 at the time of writing: §2.2 carries the
v1.3 prohibition quoted above, there is no "Changes in v1.4" section, and
`docs/spec-proposals/v1.4.md` is still present. This file is written against
v1.3's text so its quotations are accurate.

Two things from v1.4 are being relied on regardless, both confirmed out of
band: Google's scope classification as of 2026-09-21 (`drive.file`
non-sensitive, `drive.readonly` restricted with annual CASA, so §8.2 stands and
Drive is destination-only in the Play build), and §33's renumbering that makes
multi-account Dropbox v0.4 and shifts Drive down one.
