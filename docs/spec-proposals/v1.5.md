# Spec proposals for v1.5

Spec-ready text, one section per amendment, in the form I would fold into
`docs/spec.md`. The reasoning lives in `decisions.md`; this file is the wording.

Written against the spec as it stands on `main`, which is **v1.3**. The v1.4
fold does not appear in `docs/spec.md` at the time of writing — see the note at
the end of this file.

---

## 1. Amended — §2.2: reject the same *account*, not the same provider

*Rationale: §2.2 prohibits same-provider transfers in the transfer domain. That
rule was written when a provider and an account were effectively the same
thing, and the prohibition it is reaching for is real — a transfer from an
account to itself is a copy of a tree into its own subtree, which §2.3's
"copy, never synchronize" cannot express sensibly and which can recurse. But
the rule as written also forbids Dropbox → Dropbox between two accounts the
same person owns, which is a legitimate transfer and, as of v0.4, the only one
CloudLug can perform at all.*

Replace §2.2's prohibition with:

A transfer's source and destination must be different **accounts**. Two
accounts at the same provider are a legal pair; one account with itself is not.

```
Allowed:   Dropbox(A) -> Google Drive(B)    Google Drive(B) -> Dropbox(A)
           Dropbox(A) -> Dropbox(B)
Rejected:  Dropbox(A) -> Dropbox(A)
```

The rule stays in the transfer domain rather than in an adapter, as §2.2
already requires: it is a property of the pair, and no single adapter can see
both halves.

### What this changes elsewhere

- **§9** the wizard picks a source **account** and a destination **account**,
  not a provider each. Where a provider has one connected account the two
  choices look the same as before; where it has two they do not, and the
  account is what the user is actually choosing.
- **§7** is what makes the two lists differ: the source list offers accounts
  whose granted scopes permit reading, the destination list those that permit
  writing. An account may appear in both, one, or neither.
- **§12.1** the persisted transfer already records `sourceAccountId` and
  `destinationAccountId`, so nothing in storage changes. The invariant moves
  from comparing providers to comparing those two ids.

### What it does not change

§2.3 still holds: this is a copy, and a destination folder inside the source
selection would be a copy into itself. Same-account is the case that makes that
trivially reachable, which is why it stays rejected; the general case is §10's
enclosing folder and §19.3's collision rules, unchanged.

## 2. Amended — §5: what `enumerate` must emit

*Rationale: §5 says an adapter enumerates a selection and that the walk is
depth-first and resumable. It does not say what the emitted objects have to
contain, and `ManifestBuilder` needs two things §5 never asked for: each
object's `parentId`, which is how a relative path is rebuilt, and the selection
roots themselves, because §10 reproduces the source's own ancestors. The
Dropbox adapter supplied neither — it asked Dropbox for the whole subtree in
one recursive call, which returns entries with no containment between them and
never includes the folder that was asked about. Both adapters passed their
tests. The pairing that ships could not build a manifest at all.*

Add to §5, under `enumerate`:

The flow must emit, in this order:

1. **Every selection root, itself.** A root is an item of the transfer, not a
   cursor into one: §10 reproduces the source's own ancestors, and the folder
   the user selected is the outermost of them.
2. **Each root's descendants, depth-first**, each one after the object that
   contains it.

Every emitted object except a selection root must carry a non-null `parentId`
naming an object the same flow has **already** emitted. A selection root's
`parentId` is not constrained; nothing above the adapter reads it.

A selection root is not necessarily a folder. §9 offers a checkbox on every
row, so a root may be a file, and an adapter must emit it alone rather than
asking the provider to list it.

### Why this is stated rather than assumed

An adapter that satisfies §5's ordering but sets no parents at all is not
obviously broken by inspection, and it is not caught by a contract test that
asks "is each object's parent earlier in the list" — an object with no parent
passes that question by having nothing to check. The requirement has to be
"every object names a parent that came before it", which is a different
assertion and the one §31.2's suite now makes.

### What this costs

An adapter whose API offers a recursive listing may no longer use it as the
whole answer, because the containment is not in that response. Descending a
level at a time is one request per folder rather than one per page. §11 already
ranks a manifest that can be resumed above one that is built quickly, and a
manifest that cannot be built is worth nothing at either speed.

## 3. Amended — §13.1: a preparation that fails leaves PREPARING

*Rationale: §13.1 gives PREPARING the transitions READY, WAITING_FOR_WIFI,
AUTH_REQUIRED, FAILED and CANCELLED, and §24.1 shows every transfer. Nothing
said who moves a transfer out of PREPARING when preparation throws, and nothing
did: the row stayed in PREPARING with no manifest and no process behind it,
which §24.1 then displayed indefinitely as "Preparing — 0 / 0 files".*

Add to §13.1:

A transfer that enters PREPARING must leave it. If preparation does not
complete, the transfer moves to FAILED carrying the provider's error
identifier, or to the state that diagnoses the failure more precisely
(AUTH_REQUIRED, WAITING_FOR_WIFI). Cancelling the work is not a failure: the
transfer stays in PREPARING and §12.1's resume picks it up.

A state that nothing can leave is worse than a failure, because a failure at
least says what happened.

### §24.2 step 5, extended

Step 5 already says a user who reviews a manifest and backs out leaves nothing
behind. The wizard must create the transfer before §11's manifest has anywhere
to be written, so a preparation that fails leaves a row the user never
confirmed and never saw. That row is discarded with its items — a review that
never reached a manifest is abandoned in the strongest sense. This is distinct
from CANCELLED, which is how a transfer the user *did* start goes away, and
which §13.1 keeps.

## 4. Amended — §23: name the failure when the mapping has no case for it

*Rationale: §23 maps provider failures onto neutral kinds and §26 keeps
provider detail out of logs. Between them, a failure with no mapping reached
the user as "Dropbox returned 409" — a status that identifies nothing, because
409 is the status Dropbox uses for its entire route-specific error vocabulary.
The tag that does identify it was being carried on the exception and read by
nobody.*

Add to §23:

Where a provider's failure has no mapping, the message must carry the
provider's own error identifier — the tag, code or reason name, not its prose.
A bare HTTP status is not a diagnosis and is not a report anyone can act on.

This does not weaken §26. An identifier of this kind names which member of a
closed vocabulary was taken; it contains no token, no header, no filename and
no file content. It is the same string §23 already required on the exception's
`code`, and the requirement is only that whatever the user is shown includes
it.

## A note on v1.4

`docs/spec.md` on `main` is still v1.3 at the time of writing: §2.2 carries the
v1.3 prohibition quoted above, there is no "Changes in v1.4" section, and
`docs/spec-proposals/v1.4.md` is still present. This file is written against
v1.3's text so its quotations are accurate.

Two things from v1.4 are being relied on regardless, both confirmed out of
band: Google's scope classification as of 2026-09-21 (`drive.file`
non-sensitive, `drive.readonly` restricted with annual CASA, so §8.2 stands and
Drive is destination-only in the Play build), and §33's renumbering that makes
multi-account Dropbox v0.4 and shifts Drive down one.
