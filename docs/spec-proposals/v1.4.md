# Spec proposals for v1.4

Amendments ratified in principle during v0.3, written as text to fold into
`docs/spec.md`. Each came out of building against a real provider, not from
reading the spec.

The reasoning lives in `docs/decisions.md`; this file is only the wording. Where
an amendment has an ADR, it is named so the two can be read together.

---

## 1. New — §24.5 Accounts

*Rationale: ADR-0028. §4 has listed `feature/accounts/` since v1.0 and §24 never
described it, so the module that OAuth needs has been in the tree diagram for
three revisions with no specified behaviour. §8.3 requires a way to disconnect,
and disconnection has nowhere to live without this screen.*

### 24.5 Accounts

Reached from Home. One row per supported provider, whether or not an account is
connected.

```
Accounts

  Dropbox                                    Connected
  you@example.com
  Source and destination
                                           [Disconnect]

  Google Drive                           Not connected
  Needed to transfer to or from Drive
                                              [Connect]
```

A connected row shows the account's display name or email, and the roles the
account may take — source, destination, or both — derived from `grantedScopes`
(§7). Where a role is unavailable because a scope was declined at the consent
screen, the row says which scope is missing rather than silently offering fewer
options; a user who declined a permission must be able to see that this is why.

**Connect** begins the §8.1 authorization flow. **Disconnect** revokes the
tokens at the provider (§8.3) and then removes the stored credentials, in that
order: credentials removed before a successful revocation would leave a grant
alive that CloudLug can no longer revoke.

Disconnecting an account used by a transfer that is not in a terminal state
warns first, names the affected transfers, and requires confirmation. The
transfers move to `AUTH_REQUIRED` (§13.1) rather than failing, so reconnecting
the account resumes them.

Nothing on this screen shows a token, and a token is never copyable from the UI.

## 2. Amended — §22.2 cancel ordering, and new §35 exception taxonomy

*Rationale: ADR-0027. §22.2's guarantee was violated in v0.2 whenever the
cancelled file was the one in flight — the only interesting case, and one that
was unreachable until §31.3's slow-source injection existed. The guarantee holds
only under an ordering the spec did not state.*

### Addition to §22.2

Cancelling one item MUST record that item's terminal state **before** aborting
its upload session or discarding its cached chunks.

The engine decides whether a worker's failure was expected by re-reading the
item's status, so that status must already be true before anything is done that
can make the worker fail. In the other order there is a window in which the
item's row still reads as running while its session is already gone; a failure
arriving in that window is indistinguishable from a genuine fault, and ends the
whole transfer rather than the one file the user cancelled.

A failure surfacing for an item that is already terminal is **expected**. It
does not fail the transfer, does not change the item's recorded outcome, and
does not count towards any retry budget.

### New §35 subsection — exceptions out of a transfer worker

The engine applies these rules, in this order, to anything thrown out of a
worker:

1. **Cancellation propagates, always.** Pause cancels the running job (§22.1),
   and that unwinding must not be intercepted. It is re-thrown before any other
   handling, because the status re-read in rule 2 is itself a suspending
   operation and would fail on an already-cancelled coroutine.
2. **A failure for an item that settled meanwhile is absorbed**, and the run
   continues with the next item. This is the §22.2 rule above, seen from the
   engine's side.
3. **A failure for an item that is still live propagates**, unless it is a
   provider error the retry policy has already judged permanent for that item
   (§23); those mark the item `FAILED` so the transfer can still finish
   `COMPLETED_WITH_ISSUES` (§13.1). Anything else is a defect in CloudLug and
   must not be absorbed by a broad catch.

The status re-read in rule 2 reads from the database rather than from the item
the worker was given, which is a snapshot taken before the cancellation.

## 3. Amended — §5 and §19.4: upload chunk size is a multiple of the hash block

*Rationale: this constraint binds two sections that neither states it, and was
left to adapter judgement. Dropbox's `content_hash` is defined over 4 MiB
blocks; an upload chunk that ended mid-block would force a resumed upload to
re-read bytes it had already hashed, and §19.4's checkpoint to carry a partial
block across the gap.*

An adapter's upload chunk size MUST be a whole multiple of the block size of the
destination's native hash, so that every chunk boundary is also a hash block
boundary.

`ProviderCapabilities` therefore declares both: the upload chunk alignment, and
the block size of `nativeHashAlgorithm`. A provider whose native hash is not
block-structured declares a block size of one, which satisfies the rule for any
chunk size.

The consequence the rule exists to guarantee: a §19.4 checkpoint taken at a
chunk boundary never contains a partially hashed block, so an upload resumed
after a dropped connection re-sends bytes but never re-hashes them.

## 4. Amended — §26: provider headers that carry object paths

*Rationale: §26 names tokens, authorization headers and file contents. It does
not anticipate a header that is not a credential but carries user data.
Dropbox's `Dropbox-API-Arg` carries the full path of the object being operated
on, in every request.*

Add to §26:

A provider-specific header that carries object names or paths is redacted by
default, on the same footing as a credential. `Dropbox-API-Arg` is the current
example; adapters added later are assumed to have their own.

The redactor therefore allows headers by exception rather than blocking them by
exception: a header is loggable only if it is on a list of headers known to
carry no credential and no user data. A header an adapter adds later is redacted
until someone decides otherwise, which is the safe direction for an oversight.

This is the same reasoning §26 already applies to filenames — prefer opaque
identifiers, make name logging opt-in — extended to the place filenames actually
travel.

## 5. Amended — §24.2: starting a transfer leaves the wizard

*Rationale: v0.2 implemented step 6 as a wizard state, and it could never
render: starting navigates to §24.3 and removes the wizard from the back stack,
so the state existed in code and nowhere on screen.*

Add to §24.2, step 6:

Starting the transfer navigates directly to that transfer's detail screen
(§24.3), replacing the wizard rather than stacking on it, so that leaving a
started transfer returns to Home rather than to the review step. The wizard has
no "started" state of its own.

## 6. Amended — §36: `content_hash` validated for Dropbox

Add to the `content_hash` bullet in §36:

Validated for Dropbox on 2026-09-20 against a live account, by
`tools/dropbox-hash-check`: a 1-byte object, an object of exactly 4 MiB (one
whole block with no remainder), an object of ~10 MiB (two whole blocks plus a
partial), and an object already in the account that the harness did not create.
All four agreed with `core:hashing`. The equivalent check for Google Drive
remains open.

The fourth case is the one that carries the weight: the other three were
uploaded by the same code that hashed them, so only a file the harness never
touched can distinguish a correct implementation from one that is merely
self-consistent.

## 7. Amended — §11: a resume anchor that no longer exists

*Rationale: found while answering how Dropbox enumeration resumes. §5 already
permits an adapter to restart the walk rather than resume from a provider
cursor, but nothing said what happens when the anchor itself is gone. Both
adapters skipped until an id that would never arrive and emitted nothing —
producing a manifest that looked complete with no work in it. Silent, and
indistinguishable from success.*

Add to §11:

`resumeAfter` names the last object the caller persisted. That object may no
longer exist by the time enumeration resumes: the user may have deleted it, or
moved it out of the selection, between one run and the next.

An adapter MUST verify that the anchor is still present before skipping to it,
and MUST restart the walk from the beginning when it is not. An adapter MUST
NOT complete an enumeration having emitted nothing because the anchor was never
found.

Restarting is safe for the reason §5 already gives — the manifest deduplicates
by source object id, so a restart is idempotent and only slower. The failure
this rule prevents is not slowness; it is an empty manifest that the engine
cannot distinguish from a transfer with nothing left to do.

## 8. Amended — §31.4: kill during enumeration, then delete the anchor

*Rationale: §31.4 already requires killing the process during enumeration, but
that scenario only ever exercises the path where the anchor is still there on
resume. The failure above survived it.*

Add to §31.4's required scenarios:

**Kill the process during enumeration, delete the anchor object at the source,
then resume.** The resumed enumeration must walk the whole selection again and
produce a manifest equivalent to one built without interruption. An
implementation that emits nothing, or that fails, does not satisfy this.

The existing "kill during enumeration" scenario is necessary but not
sufficient: it holds the source still, and a source that holds still is the case
least likely to break. The point of §31.4 is the source that does not.

## 9. Amended — §8.3: an unreadable credential is reported before it is forgotten

*Rationale: §8.3 says a stored credential that cannot be decrypted is treated as
absent, so the user reconnects rather than the app crashing. That is right, but
as written it makes three different events indistinguishable to everything above
the credential store: nothing was ever stored here, the Keystore key was
destroyed, and someone edited the app's preferences file. The first is ordinary,
the third is an attack, and silence is the same answer for both.*

Add to §8.3:

A credential that is present but cannot be decrypted is logged at warning level
before it is treated as absent. Absence itself is not logged: it is the ordinary
first-run path, and a warning there is the noise that trains people to ignore
the warning that matters.

The log records the storage key — `dropbox`, not the credential — and a failure
class, and nothing else. §26 already forbids the credential material; this adds
that the exception's own message is not logged either, since it is written
elsewhere and its contents are not this app's to vouch for.

Two failure classes are distinguished, because they are different events:

- **The Keystore key no longer exists.** A factory reset, a restored backup, or
  an OEM discarding keys on a lock-screen change. The ciphertext left behind is
  inert and nobody did anything wrong.
- **The key exists and the stored bytes did not authenticate.** AES-GCM is
  authenticated, so this is a file that was edited after it was written.

Telling them apart takes deliberate care in the implementation, and the obvious
implementation gets it wrong: a reader that asks for the key through the usual
generate-on-first-use accessor will silently mint a fresh key when the old one
is gone, fail to decrypt with it, and report a destroyed key as a failed
authentication tag — reporting an attack every time a user restores a phone. A
credential read must therefore look the key up without creating it, and report a
missing key as a missing key.

## 10. Amended — §8.1: the return trip, and a device with no browser

*Rationale: added after v0.3 merged. §8.1 specifies the outward leg of the
sign-in — a Custom Tab rather than a WebView, PKCE, the registered redirect —
and says nothing about coming back. v0.3 shipped green on three CI jobs and
crashed on a real phone the instant the consent screen handed control back,
because the library activity that receives the redirect runs under the app's
theme and needs one of its own. The bug was not in any code that handles a
redirect; it was in starting the activity at all, which nothing had ever done.*

Add to §8.1:

The component that receives the redirect is part of the sign-in and is
specified as such. Where a library supplies it, the app is responsible for the
configuration that component needs — its theme, its exported state, and the
scheme it claims — because a redirect that cannot be received fails after the
user has already granted consent, which is the worst place in the flow to fail.

A build is not considered to satisfy §8.1 until the redirect has been
delivered to that component at least once by an automated test. Driving a real
browser is not required and generally not possible in CI; delivering the
redirect directly to the receiving component, as the browser would, is enough,
and is what §31.4 should require.

Add to §8.1:

If no browser is available, the app says so and stops. §8.1 requires a browser
precisely so the app never sees the user's credentials, so its absence is a
genuine dead end — but the user is told that sign-in needs a browser, rather
than shown a crash. A managed device, a stripped-down build and an emulator
running an AOSP image can all lack one.

*Note on why this is one section rather than two: both halves are the same
omission. §8.1 describes the sign-in as something the app starts, and both
failures are in what happens when control comes back — or cannot leave in the
first place.*
